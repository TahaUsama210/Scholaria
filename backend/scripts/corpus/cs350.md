## Processes and fork()

A process is a program in execution: an address space holding code, data, heap and stack, together with one or more threads of execution and operating system resources such as open file descriptors. The kernel tracks each process in a process control block, PCB, which stores its process identifier, PID, its state (new, ready, running, blocked or terminated), saved registers, scheduling information and memory-management information.

On UNIX systems new processes are created with the fork() system call. fork() creates a child process that is a near-exact duplicate of its parent: the same code, a copy of the address space, and copies of the open file descriptors, which share file offsets with the parent. fork() is called once but returns twice. In the child it returns 0; in the parent it returns the PID of the new child; on failure it returns -1 in the parent and no child is created. Programs branch on this return value to give parent and child different work.

Copying the whole address space would be wasteful, especially since many children immediately replace their program. Modern kernels therefore use copy-on-write: parent and child initially share all physical pages, marked read-only, and a page is copied only when one of them writes to it, which triggers a protection fault that the kernel handles.

The exec() family of calls, such as execve(), replaces the program running in the calling process with a new one while keeping the PID and the open descriptors. A shell runs a command by calling fork(); the child calls exec() on the program while the parent waits.

A parent collects a child's exit status with wait() or waitpid(). When a child exits, most of its resources are freed, but its entry in the process table remains as a zombie until the parent calls wait(), so that the exit status can still be reported. A parent that never waits leaks zombies. If the parent exits first, the child becomes an orphan and is adopted by init, PID 1 on Linux, which reaps it when it terminates.

## Signals

A signal is an asynchronous notification delivered to a process by the kernel, used to report events such as a keyboard interrupt, an illegal memory access or the termination of a child. Each signal has a number and a default action: terminate the process, terminate and dump core, stop the process, continue it, or ignore the signal.

Common signals include SIGINT, sent when the user presses Ctrl-C at the terminal; SIGTERM, the polite default request to terminate, sent by the kill command; SIGSEGV, raised by the kernel on an invalid memory reference; SIGCHLD, sent to a parent when one of its children stops or terminates; SIGALRM, delivered when a timer set with alarm() expires; and SIGHUP, sent when the controlling terminal hangs up and conventionally used to ask daemons to reload their configuration.

Processes send signals with the kill() system call or the kill command, which despite its name can send any signal. A process may install a handler with sigaction() or the older signal() call to catch a signal and run its own code, or it may choose to ignore the signal. It can also block signals temporarily with sigprocmask(), in which case they stay pending until they are unblocked.

Two signals are special. SIGKILL (signal 9) and SIGSTOP cannot be caught, blocked or ignored. SIGKILL always terminates the target immediately, which guarantees that an administrator can stop a runaway process, but the process gets no chance to flush buffers, remove temporary files or release external resources. For that reason shutdown sequences send SIGTERM first and escalate to SIGKILL only if the process has not exited after a grace period; container runtimes such as Docker do exactly this. SIGSTOP suspends a process unconditionally and SIGCONT resumes it, while the catchable SIGTSTP is what Ctrl-Z sends.

Signal handlers run asynchronously, interrupting the program at an arbitrary instruction, so they may only call async-signal-safe functions such as write(). They must not call printf() or malloc(), which may hold internal locks. A common pattern is for the handler to set a volatile sig_atomic_t flag that the main loop checks.

## CPU Scheduling

The CPU scheduler decides which ready process or thread runs next on each core. A non-preemptive scheduler switches only when the running task blocks or exits, while a preemptive scheduler can interrupt it, typically on a timer interrupt. The goals conflict: high throughput, low turnaround time (completion minus arrival), low response time (first run minus arrival) for interactive tasks, and fairness between tasks.

First-come, first-served, FCFS, runs jobs in arrival order. It is simple but suffers from the convoy effect: one long CPU-bound job at the head of the queue makes many short jobs wait behind it. Shortest job first, SJF, and its preemptive form, shortest remaining time first, minimise average turnaround time, but they need to know burst lengths in advance, which are usually estimated with an exponential average of past bursts, and they can starve long jobs.

Round robin gives each ready task a fixed time slice, the quantum, typically a few milliseconds, then preempts it and moves it to the back of the ready queue. Response time is good and no task starves. The quantum is a trade-off: too short and context-switch overhead dominates, too long and round robin degenerates into FCFS.

Priority scheduling always runs the highest-priority ready task. Low-priority tasks can starve, which is fixed by aging, gradually raising the priority of tasks that have waited a long time. Priority inversion occurs when a high-priority task waits for a lock held by a low-priority task that is itself preempted by medium-priority work; priority inheritance temporarily boosts the lock holder.

The multi-level feedback queue, MLFQ, approximates SJF without knowing the future. New tasks start at the top priority, a task that uses up its whole quantum moves down a level, and tasks that block for I/O early stay high, so interactive tasks remain responsive; periodic priority boosts prevent starvation.

The Completely Fair Scheduler, CFS, the Linux default from version 2.6.23 until EEVDF replaced it in 6.6, tracks each task's virtual runtime, vruntime, the CPU time it has received weighted by its nice value. It always runs the task with the smallest vruntime, kept in a red-black tree, so CPU time is shared in proportion to the weights.

## Threads and Synchronisation

A thread is an independent sequence of execution within a process. Threads of the same process share the address space, heap, global variables and open files, but each has its own stack, registers and program counter. Creating and switching between threads is cheaper than for processes, and shared memory makes communication easy, but it also makes races possible.

A race condition occurs when the result depends on the timing of operations on shared data. The statement counter++ compiles to a load, an add and a store; if two threads interleave those steps, one increment can be lost. Code that accesses shared state is a critical section, and a correct solution must provide mutual exclusion, so that at most one thread is inside it, as well as progress and bounded waiting.

Locks are built on atomic hardware instructions. Test-and-set atomically writes 1 to a word and returns its old value; compare-and-swap, CAS, writes a new value only if the word still holds an expected value. A spinlock loops on such an instruction until it acquires the lock. It burns CPU time while waiting, so it suits only very short critical sections, and on a single core spinning is pure waste because the holder cannot run until the spinner is preempted. A mutex instead puts the waiting thread to sleep in the kernel and wakes it when the lock is released, as with pthread_mutex_lock() and pthread_mutex_unlock().

A semaphore is an integer counter with two atomic operations: wait, also called P, decrements it and blocks if the result would be negative, and signal, also called V, increments it and wakes a waiter. A binary semaphore acts like a lock, while a counting semaphore initialised to N admits up to N threads at once, for example to manage a pool of N buffers.

A condition variable lets a thread sleep until some condition on shared state becomes true. It is always used together with a mutex: wait atomically releases the mutex and sleeps, and signal or broadcast wakes waiters, which reacquire the mutex before returning. Waiters must recheck the condition in a while loop, because wakeups can be spurious. The bounded-buffer producer-consumer problem is the standard exercise for combining these tools.

## Deadlock

A deadlock is a state in which every thread in a set is blocked waiting for a resource held by another thread in the same set, so none of them can ever proceed. The simplest case involves two locks: thread 1 holds lock A and requests lock B while thread 2 holds lock B and requests lock A.

Coffman identified four conditions that must all hold for a deadlock to occur. Mutual exclusion: at least one resource can be held by only one thread at a time. Hold and wait: a thread holds at least one resource while waiting to acquire others. No preemption: resources cannot be forcibly taken from the thread holding them and are released only voluntarily. Circular wait: there is a cycle of threads, each waiting for a resource held by the next one in the cycle.

Deadlock prevention removes one of the conditions by design. The most practical technique breaks circular wait with lock ordering: every thread acquires locks in the same global order, for example by lock address, so no cycle can form. Hold and wait can be removed by acquiring all needed locks at once, or by using trylock and releasing everything already held when an attempt fails. Preemption works for some resources, such as CPU time or memory pages, but not for a lock that protects half-updated data.

Deadlock avoidance makes decisions dynamically. The banker's algorithm requires each thread to declare its maximum demand in advance and grants a request only if the resulting state is safe, meaning that there exists some order in which every thread can obtain its maximum and finish. It is elegant but rarely used, since maximum demands are seldom known.

Deadlock detection lets deadlocks happen and then recovers. With single-instance resources the system builds a wait-for graph, with an edge from each thread to the thread it waits on, and searches it for a cycle; recovery aborts or rolls back a victim. Database systems take exactly this approach for transaction locks. General-purpose kernels mostly leave application deadlocks to programmers, an approach sometimes called the ostrich algorithm.

Livelock is a related failure in which threads keep changing state in response to each other, for example by repeatedly backing off and retrying, without making any progress.

## Virtual Memory and Page Tables

Virtual memory gives every process the illusion of a large, private, contiguous address space. The hardware memory management unit, MMU, translates each virtual address used by a program into a physical address in RAM. This isolates processes from one another and lets the operating system place pages anywhere in physical memory or on disk.

With paging, the virtual address space is divided into fixed-size pages and physical memory into frames of the same size, commonly 4 KiB. A virtual address splits into a virtual page number and an offset within the page; translation replaces the page number with a frame number and keeps the offset. The mapping is stored in the page table, one per process. Each page table entry, PTE, holds the frame number plus control bits: a valid or present bit, protection bits for read, write and execute permission, a dirty bit set when the page is written, and a referenced or accessed bit set when it is used. Touching a page whose valid bit is clear raises a page fault, and the kernel decides whether to load the page from disk or to kill the process.

A flat page table for a large address space would be enormous and would mostly describe unused memory, so real systems use multi-level page tables, a radix tree indexed by successive pieces of the virtual page number. On x86-64 with 4 KiB pages, a 48-bit virtual address is split into four 9-bit indices and a 12-bit offset; each level is a 4 KiB table of 512 eight-byte entries, and the CR3 register points to the top level. Subtrees for unmapped regions are simply absent. The cost is that one translation can need four memory accesses, a page walk.

The translation lookaside buffer, TLB, is a small, fast associative cache of recent translations inside the MMU. Most accesses hit in the TLB, so page walks are rare, but a context switch may require flushing it unless its entries are tagged with address-space identifiers. Huge pages of 2 MiB or 1 GiB let one TLB entry cover far more memory. Inverted page tables, with one entry per physical frame located by hashing, are an alternative design used on some architectures.

## Page Replacement and Thrashing

Demand paging loads a page into memory only when it is first accessed. When a page fault occurs and no frame is free, the operating system must choose a victim page to evict, and if the victim is dirty it must be written back to swap space before its frame can be reused. Because a page fault that goes to disk costs many thousands of times more than a memory access, the choice of victim matters enormously.

The optimal policy, OPT or Belady's MIN, evicts the page that will not be used for the longest time in the future. It cannot be implemented, since it requires knowledge of future references, but it is the yardstick against which practical policies are measured. FIFO evicts the page that has been resident longest. It is simple but ignores usage, and it suffers from Belady's anomaly: for some reference strings, giving the process more frames increases the number of page faults. The reference string 1 2 3 4 1 2 5 1 2 3 4 5 causes 9 faults with three frames but 10 with four.

LRU, least recently used, evicts the page whose last access lies furthest in the past, using recent history as a predictor of the future. LRU is a stack algorithm, so it never exhibits Belady's anomaly. Exact LRU would require updating a timestamp or a list on every memory reference, which is far too expensive, so kernels approximate it. The clock, or second-chance, algorithm arranges the frames in a circle and uses the referenced bit that the MMU sets in each page table entry: the hand clears set bits as it passes and evicts the first page it finds whose bit is already clear. Variants also consider the dirty bit and prefer clean pages, which need no write-back.

The working set of a process is the set of pages it referenced within a recent window of time. If the working sets of all running processes together exceed physical memory, the system thrashes: processes fault continuously, the CPU sits idle waiting for the disk, and throughput collapses. The remedy is to reduce the degree of multiprogramming by suspending or swapping out whole processes, or to add memory. As a last resort, the Linux out-of-memory killer terminates a process to free its memory.

## File Systems and Journaling

A file system maps named files onto the blocks of a storage device. In UNIX-style file systems each file is described by an inode, which holds its metadata, including owner, permissions, size and timestamps, and the locations of its data blocks, but not its name. A directory is a special file that maps names to inode numbers. Small files are reached through direct block pointers in the inode and larger ones through single, double and triple indirect blocks; ext4 instead uses extents, each describing a contiguous run of blocks.

A hard link is an additional directory entry pointing to the same inode. The inode keeps a link count, so the file is deleted only when its last link is removed, and hard links cannot span file systems or point to directories. A symbolic link, or soft link, is a small file containing a path name, which dangles if its target is removed.

Updating a file usually touches several structures at once: appending a block modifies the free-block bitmap, the inode and the data block itself. A crash between these writes leaves the file system inconsistent, for example with a block marked as used that no file references. Early systems ran fsck after every crash to scan the whole disk and repair such inconsistencies, which can take hours on large volumes.

Journaling file systems solve crash consistency by writing a description of each update to a journal, a reserved log area, before applying it in place. A transaction is written to the journal and followed by a commit block, and only after the commit block is durable are the changes checkpointed to their final locations. After a crash, recovery replays the committed transactions in the journal and discards incomplete ones, which takes seconds. Metadata journaling in ordered mode, the ext4 default, logs only metadata but forces data blocks to disk before the related metadata commits, so files never point at garbage; full data journaling also logs file contents, at the cost of writing all data twice.

Copy-on-write file systems such as ZFS and Btrfs never overwrite live data: they write modified blocks to new locations and then atomically switch the root pointer, which also makes snapshots cheap. Applications still need fsync() to force their own data to stable storage at a known point.
