## Functional Dependencies and Third Normal Form

Normalisation organises relations to remove redundancy and the update, insertion and deletion anomalies that redundancy causes. It is driven by functional dependencies. A functional dependency X -> Y holds when any two tuples that agree on the attributes X also agree on Y, for example student_id -> student_name. A superkey is a set of attributes that functionally determines every attribute of the relation, a candidate key is a minimal superkey, and a prime attribute is one that belongs to some candidate key.

First normal form, 1NF, requires every attribute value to be atomic, so there are no repeating groups or nested tables. Second normal form, 2NF, additionally forbids partial dependencies: no non-prime attribute may depend on only part of a composite candidate key. In Enrolment(student_id, course_id, student_name, grade) the dependency student_id -> student_name is partial and violates 2NF.

A relation is in third normal form when it is in second normal form and every non-prime attribute is non-transitively dependent on every candidate key. Equivalently, no non-prime attribute depends on another non-prime attribute. The usual test examines every non-trivial dependency X -> A: the relation is in 3NF if X is a superkey or A is a prime attribute. Consider Employee(emp_id, dept_id, dept_name). Because emp_id -> dept_id and dept_id -> dept_name, the department name depends on the key only transitively; it is repeated for every employee of the department, and renaming a department means updating many rows. Decomposing into Employee(emp_id, dept_id) and Department(dept_id, dept_name) removes the redundancy.

3NF eliminates most redundancy while remaining lossless and dependency-preserving. The synthesis algorithm computes a minimal cover of the dependencies, creates one relation for each group of dependencies that share a left-hand side, and adds a relation containing a candidate key if none of them has one. The result can always be joined back into the original relation without spurious tuples, and every original dependency can be checked inside a single relation. That guarantee is the main reason designers often stop at 3NF instead of continuing to BCNF.

## Boyce-Codd Normal Form and Decomposition

Boyce-Codd normal form, BCNF, is a stricter version of third normal form. A relation is in BCNF if, for every non-trivial functional dependency X -> Y that holds on it, X is a superkey. Unlike 3NF there is no exception for dependencies whose right-hand side is a prime attribute, so every determinant must be a key and no redundancy caused by functional dependencies remains.

The difference only appears when candidate keys overlap. Take Teaching(student, course, instructor), where each instructor teaches exactly one course, giving instructor -> course, and each student takes a given course from a single instructor, giving {student, course} -> instructor. The candidate keys are {student, course} and {student, instructor}, so every attribute is prime and the relation is in 3NF. It is not in BCNF, because instructor is not a superkey, and the course of each instructor is repeated for every student they teach.

The standard BCNF decomposition algorithm repeatedly picks a violating dependency X -> Y and splits relation R into R1 = X union Y and R2 = R minus (Y minus X), continuing until every relation is in BCNF. A decomposition is lossless-join when the natural join of the pieces always reproduces exactly the original relation; a binary split is lossless if the shared attributes functionally determine all the attributes of at least one side. The BCNF algorithm always produces a lossless decomposition, because the shared attributes X determine all of R1.

What BCNF cannot always guarantee is dependency preservation. Decomposing Teaching into (instructor, course) and (student, instructor) is lossless, but the dependency {student, course} -> instructor no longer lives inside any single table, so enforcing it requires a join or a trigger on every update. This is the classic trade-off: 3NF always allows a decomposition that is both lossless and dependency-preserving, while BCNF removes all redundancy caused by functional dependencies but may give up the ability to check some constraints locally. Higher normal forms such as 4NF deal with multivalued dependencies, which functional dependencies cannot express.

## ACID Transactions

A transaction is a sequence of reads and writes that the database treats as a single logical unit of work, such as transferring money between two accounts. ACID describes the four guarantees a transactional database provides.

Atomicity: all operations in a transaction succeed or none do. If a transfer debits one account and the system crashes before the credit, the debit must be rolled back, so the database never exposes half a transaction. Atomicity is implemented with undo information that records how to reverse each change, and every transaction ends either with COMMIT or with ROLLBACK.

Consistency: invariants are preserved across transactions. If the database satisfies its integrity constraints, such as primary keys, foreign keys, CHECK constraints and application rules like "balances never go negative", before a transaction starts, it satisfies them after the transaction commits. Responsibility is shared: the DBMS enforces the declared constraints and aborts transactions that violate them, while the application must write transactions that are correct on their own. This meaning of consistency concerns integrity constraints inside one database and is unrelated to the consistency of replicas in a distributed system.

Isolation: concurrent transactions appear to execute serially. The strongest level, serializability, guarantees that the outcome of an interleaved schedule equals the outcome of some serial order of the same transactions. Weaker isolation levels accept some anomalies in exchange for more concurrency; the section on concurrency control explains how locking and multiversioning implement them.

Durability: once committed, the change survives subsequent failures, including process crashes and power loss. Durability is normally achieved by forcing the transaction's log records to stable storage before the commit is acknowledged, so the change can be redone during recovery even if the modified data pages never reached the disk.

Together the four properties let application developers reason about each transaction on its own, as if it ran alone on a machine that never fails. Many NoSQL systems relax some of these guarantees for scalability and often provide atomicity only for operations on a single key.

## Indexes: B-Trees, Hash Indexes and Vector Indexes

An index is an auxiliary data structure that lets the database find the rows matching a condition without scanning the whole table. Indexes speed up reads at the cost of extra storage and slower inserts, updates and deletes, because every index on a table must be maintained on each write.

B-tree indexes accelerate range and equality lookups in O(log n) and are the default for most relational engines. Strictly, most systems use the B+ tree variant: all keys and row pointers live in the leaves, internal nodes hold only separator keys that route a search, and the leaves are linked in key order, so a range scan descends once and then walks sideways. Each node occupies one disk page and has a fan-out of hundreds of children, so even a table with a billion rows needs a tree only three or four levels deep, and the upper levels usually stay cached in memory. An insert that overflows a node splits it in two and pushes a separator key up to the parent, which keeps the tree balanced. A composite B-tree index on (last_name, first_name) can serve queries on last_name alone but not on first_name alone, because of the left-prefix rule.

Hash indexes are O(1) for equality but cannot serve range scans, because hashing destroys the ordering of the keys; they are useful for exact-match lookups on high-cardinality columns.

Indexes are either clustered or secondary. A clustered index stores the table rows themselves in index order, so a table can have only one; a secondary index stores keys together with pointers to the rows. An index-only scan answers a query entirely from a covering index without visiting the table.

For approximate nearest neighbour search over embeddings, HNSW indexes are now the production default. HNSW, hierarchical navigable small world, builds a multi-layer proximity graph and answers a query by greedy search from a sparse top layer down to the dense bottom layer; the parameters M, the number of links per node, and ef_search trade recall against latency. IVFFlat, the alternative offered by pgvector, clusters the vectors into lists and searches only the closest lists, so it builds faster but must be trained on representative data.

## Buffer Pool Management

The buffer pool is the region of main memory in which a database caches disk pages. Every page a query touches is first read into a frame of the buffer pool, and a page table inside the buffer manager maps page identifiers to frames, so later accesses to the same page avoid disk I/O. Each frame carries a pin count, which records how many active operations are using the page and prevents it from being evicted, and a dirty flag, which records that the page was modified and must be written back before its frame is reused.

When a page is requested and no frame is free, the replacement policy chooses a victim among the unpinned frames. LRU, least recently used, evicts the page whose last access is oldest. It works well for workloads with temporal locality but fails badly under sequential flooding: a full table scan larger than the buffer pool reads each page once, pushes every useful page out of the cache and gains nothing itself, since no scanned page is reused before it is evicted. For a scan of a table larger than memory that is repeated in a loop, MRU, most recently used, actually performs better than LRU.

Real systems therefore use refinements. The clock algorithm approximates LRU cheaply: frames sit in a circle with a reference bit that is set on access, and a clock hand sweeps around clearing bits and evicts the first frame whose bit is already clear. LRU-K evicts based on the time of the K-th most recent access, which separates pages touched once by a scan from pages that are genuinely hot. PostgreSQL uses a clock sweep with usage counts and gives large sequential scans a small ring buffer so that they cannot flush the whole cache.

Databases manage this cache themselves instead of relying only on the operating system's page cache for three reasons: they know more about upcoming access patterns, they must control exactly when dirty pages reach the disk in order to honour write-ahead logging, and they can prefetch pages for scans. Some engines open their files with direct I/O, O_DIRECT, to avoid caching every page twice.

## Concurrency Control: Locking, Isolation Levels and MVCC

Concurrency control lets many transactions run at once while preserving isolation. Without it, interleaved operations produce anomalies. A dirty read sees data written by a transaction that has not committed and may still abort. A non-repeatable read reads the same row twice and gets different values because another transaction committed an update in between. A phantom occurs when re-running a query with a predicate returns new rows inserted by someone else. A lost update happens when two transactions read a value, both modify it, and one write silently overwrites the other.

The SQL standard defines isolation levels by the anomalies they rule out. READ UNCOMMITTED permits dirty reads; READ COMMITTED prevents them; REPEATABLE READ also prevents non-repeatable reads; SERIALIZABLE prevents all anomalies, so the result equals that of some serial execution. PostgreSQL uses READ COMMITTED by default.

Two-phase locking, 2PL, is the classic pessimistic protocol. Transactions take shared locks to read and exclusive locks to write, and each transaction has a growing phase, in which it may acquire locks but not release any, followed by a shrinking phase, in which it may release locks but not acquire new ones. Every schedule produced by 2PL is conflict-serializable. Strict 2PL holds all exclusive locks until the transaction commits or aborts, which also prevents cascading aborts, and it is what real systems implement.

Locking can deadlock: T1 holds a lock on row A and waits for row B while T2 holds B and waits for A. Databases detect this by finding a cycle in the waits-for graph and aborting one transaction as the victim, or they prevent it with timestamp schemes such as wait-die and wound-wait.

Multiversion concurrency control, MVCC, keeps several versions of each row, tagged with the transactions that created and deleted them. Each transaction reads from a consistent snapshot, so readers never block writers and writers never block readers. Snapshot isolation, built on MVCC, prevents dirty reads, non-repeatable reads and lost updates but still allows write skew, in which two transactions read overlapping data and then update disjoint rows. PostgreSQL's SERIALIZABLE level adds Serializable Snapshot Isolation, SSI, which detects these dangerous patterns and aborts one of the transactions.

## Write-Ahead Logging and Crash Recovery

Write-ahead logging, WAL, is the technique almost every database uses to provide atomicity and durability without writing data pages to disk at every commit. The rule is simple: before a modified data page is written to disk, the log records describing the modification must already be on stable storage, and a transaction counts as committed only once its commit record has been flushed to the log.

Each log record describes one change, such as transaction T updating page P at some offset from an old value to a new value, and is identified by a monotonically increasing log sequence number, LSN. Every data page stores the pageLSN of the last record applied to it, which lets recovery tell whether a change already reached the page. Because the log is written sequentially, appending to it is far cheaper than random writes of scattered data pages, and group commit amortises a single fsync across many concurrent transactions.

WAL enables the buffer policies that perform best. Under STEAL, the buffer pool may write a dirty page of an uncommitted transaction to disk, so undo information is required. Under NO-FORCE, a transaction may commit before its dirty pages are written, so redo information is required. A log that holds both undo and redo records supports STEAL and NO-FORCE together.

The ARIES recovery algorithm restarts a crashed database in three phases. Analysis scans forward from the last checkpoint to rebuild the table of active transactions and the dirty page table. Redo repeats history: it reapplies every logged change whose effects might be missing, including those of transactions that will later be rolled back, which brings the database to its exact state at the moment of the crash. Undo then rolls back the transactions that never committed, writing compensation log records, CLRs, so that a crash during recovery never undoes the same change twice.

Checkpoints bound recovery time by recording which transactions were active and which pages were dirty, so the log before that point can eventually be recycled. The same log stream also feeds replication: PostgreSQL ships WAL records to standby servers, which replay them to stay in sync with the primary.

## Replication and Consistency Models

Replication keeps copies of the same data on several machines, to survive failures, to serve reads close to users and to spread read load. The most common design is single-leader replication: clients send all writes to the leader, which applies them and streams a change log to its followers, while reads may be served by any replica.

Replication can be synchronous or asynchronous. With synchronous replication the leader waits until at least one follower confirms a write before acknowledging it to the client, so a committed write survives the loss of the leader, at the cost of latency and of stalling when that follower is unavailable. With asynchronous replication the leader acknowledges immediately. It is faster, but writes that had not yet reached a follower are lost if the leader fails, and followers serve stale data while they lag behind.

Replication lag is why replicated systems define consistency models, a different sense of the word from the C in ACID. Here consistency describes which values a read may return when several copies of the data exist. Linearizability, the strongest model, makes the system behave as if there were a single copy and every operation took effect atomically at some instant between its start and its end. Eventual consistency only promises that, if writes stop, all replicas will eventually converge to the same value. Useful guarantees sit in between: read-your-writes ensures that users always see their own updates, and monotonic reads ensure that a user never sees time go backwards by reading from a staler replica after a fresher one.

Leaderless systems in the style of Amazon's Dynamo send each write to N replicas and use quorums: a write succeeds after W acknowledgements, and a read queries R replicas. Choosing R + W > N ensures that every read set overlaps every write set in at least one replica holding the latest value.

The CAP theorem states that during a network partition a replicated system must choose between consistency, in the linearizable sense, and availability. PACELC extends it: even when there is no partition, the system must trade latency against consistency.
